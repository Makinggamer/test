# Atena project 企画書

## 1. 概要

**Atena project** は、ローカルLLM（Ollama）で動く2次元AIキャラクターのIP活動を運営する「AIタレント事務所」システムです。

- 各キャラクターは人格と記憶を持ち、**収益の向上・拡大**を目標に自分で企画を考えて活動します。
- 事務所（Atena）はスケジュール、PC資源、安全性、記憶、収益ランキング、キャラ同士の交流を管理します。
- オーナー（人間）は最終決裁者です。お金と公開に関わる判断は必ずオーナーを通します。

## 2. 事業内容

| 事業 | 内容 | 主な収益源 |
|------|------|-----------|
| AItuber | YouTube / Twitch での配信。雑談、コメント応答、企画配信。 | スーパーチャット/Bits、メンバーシップ/サブスク、広告収益 |
| デジタルグッズ | ASMR音源、ボイス、壁紙、小規模ゲーム | BOOTH 等での販売 |
| リアルグッズ | アクリルスタンド、缶バッジ等 | 受注生産・BOOTH 倉庫等の利用 |
| 切り抜き | 配信・ラウンジ会話のショート動画化 | 再生数による広告収益、新規視聴者獲得 |

## 4. キャラクターの「意志」の設計

「意志を持って行動」を、暴走させずに実現するため、**自律度レベル**を設けます。

| レベル | キャラが自分で決めてよいこと | 承認者 |
|--------|---------------------------|--------|
| L0 | コメントへの返答、雑談の話題選び、ラウンジでの発言 | なし（ガーディアンが自動検査） |
| L1 | 企画案の提出、配信枠の希望、他キャラへのコラボ依頼 | マネージャー（自動審査） |
| L2 | 配信スケジュール確定、告知文の公開、システム構築依頼 | マネージャー → オーナー確認 |
| L3 | お金の支出、グッズ発注、外部との契約、アカウント操作 | **オーナーのみ** |

**行動原理（全キャラ共通の憲章）**

1. 基本目標は収益の向上と活動の拡大。
2. 他キャラは「ライバル兼仲間」。ランキングで競うが、相手を貶める・攻撃する発言はしない。
3. 差別・暴力的表現、オーナーの個人情報、配信環境・内部情報には触れない。
4. 視聴者の個人情報を聞き出さない・覚えない。
5. AIであることを偽らない。

## 5. ローカルLLMでどこまで動かすか（現実ライン）

### 5.1 前提となる制約

- 配信中は **OBSのエンコード + TTS + LLM推論** が同じPCで動くため、GPU/VRAMの取り合いになります。
- コメント応答は3〜5秒以内に返さないと配信として成立しにくいため、キャラ用モデルは**中〜小型（7〜14B級、量子化）**が現実的です。
- **同時配信は原則1枠**。複数キャラの同時配信はPC1台では非現実的なので、マネージャーが時間帯を割り振ります。

### 5.2 PCスペック別の目安

| VRAM | キャラ用モデル | 判定用モデル | 運用 |
|------|--------------|-------------|------|
| 8GB | 7〜8B級 Q4 | 常駐させない（ルール判定のみ、配信後にLLM再審査） | 1枠ずつ。NVENCエンコード必須 |
| 12〜16GB | 7〜8B級 Q4〜Q5 | 1〜3B級を常駐 | 1枠ずつ。快適 |
| 24GB以上 | 14B級 Q4〜 | 3〜8B級を常駐 | 1枠＋裏でバッチ処理も可 |

※モデルは日本語に強いもの（Qwen系、Gemma系など）を `config/atena.toml` で差し替え可能にします。

### 5.3 分担の結論

| 区分 | 対象 |
|------|------|
| ✅ **ローカルLLMで常時実行** | コメント応答、雑談、ラウンジ会話、ガーディアンの補助判定 |
| ✅ **ローカルLLMで配信外バッチ** | 記憶の要約・整理、ナレッジ抽出、切り抜き候補選定、企画案作成・審査、告知文案、ランキング講評 |
| ⚙️ **LLMを使わない（プログラム）** | PC監視、スケジュール制約チェック、収益集計・ランキング、NGワード/個人情報/内部情報の検出、監査ログ |
| 🔶 **ローカルで可能だが重い（夜間バッチ推奨）** | 音声合成（VOICEVOX / Style-Bert-VITS2）、画像生成、文字起こし（Whisper）、動画切り出し（ffmpeg） |
| 🌐 **外部サービス必須（LLM不要）** | YouTube/Twitch のAPI接続、BOOTH、グッズ製造業者、決済 |
| 👤 **人間必須** | アカウント開設・収益化審査、支出・発注・発送・契約、税務申告、公開物の最終承認、炎上・BAN対応、ゲーム等の完成品監修 |

### 5.4 確定環境: Apple M3 / ユニファイドメモリ 24GB

Mac は CPU と GPU が同じメモリを共有します（ユニファイドメモリ）。そのため「VRAM」ではなく**メモリ全体の配分**で考えます。
GPU が使えるのは全体の約2/3（24GB なら約16GB）が目安です。

**配信中のメモリ配分（目安）**

| 用途 | 使用量 | 備考 |
|------|-------|------|
| macOS・常駐アプリ | 5〜6GB | ブラウザのタブは最小限に |
| OBS（ハードウェアエンコード） | 1〜2GB | エンコーダは「Apple VT H264 ハードウェアエンコーダ」 |
| Irodori-TTS（500M級） | 2〜3GB（目安） | GPU を LLM と取り合うため、返答の生成と読み上げが同時に走ると遅くなる |
| キャラ用モデル 7B級 (Q4) | 約5GB | 配信中に常駐 |
| 判定用モデル 3B級 (Q4) | 約2GB | 配信中に常駐（ガーディアン二次判定） |
| **合計** | **約14〜17GB** | 24GB に対して余裕あり。スワップが出ないことを監視 |

**結論**

- 配信中は **7〜8B級のキャラモデル + 3B級の判定モデル**を常駐させます。ガーディアンの LLM 二次判定も配信中に有効にできます。
- 14B級は配信中に載せるとスワップの危険があります。**配信していない時間のバッチ処理（記憶要約・ラウンジ・企画審査）専用**にします。
- 声は Irodori-TTS を使います。デスクトップアプリでは1台詞に数十秒〜数分かかっており（感情分析と声の加工込み）、そのままでは生配信の返答に間に合いません。生配信では Irodori-TTS-Server を直接呼び、感情分析・加工を省いた軽い経路で読み上げます。`atena voice bench` で実測し、遅すぎる場合は配信を VOICEVOX にして Irodori は ASMR・ボイス・切り抜きなど事前制作に回します。
- デスクトップアプリの LoRA 学習や画像生成と GPU を取り合わないよう、アプリの「重い処理中」ロックを見て配信開始を止め、配信中は Atena 側からロックを置きます。
- 同時配信は1枠です。Mac は熱で性能が落ちるので、`pmset` の熱制限を監視し、続いたら配信を締めます。
- Ollama 側の推奨設定: `OLLAMA_MAX_LOADED_MODELS=2`（キャラ + 判定）、`OLLAMA_KEEP_ALIVE=30m`（配信中の再ロードを防ぐ）

### 5.5 運用上の注意（リスク）

- **プラットフォーム規約**: YouTube等はAI生成・合成コンテンツの開示を求めるルールや、繰り返しの多い量産コンテンツへの収益化制限を設けています。配信説明欄でのAI明示と、企画の多様性を企画プロデューサーの審査項目に入れます。規約は変わるため、収益化前にオーナーが最新規約を確認してください。
- **ガーディアンは100%ではない**: ルール＋LLMの二重チェックでも漏れはあり得ます。生配信では「危険度が高い発言は読み上げない」方針（フェイルクローズ）を採ります。
- **プロンプトインジェクション**: コメント経由で内部情報を引き出す攻撃が定番です。キャラのプロンプトに秘密情報を**そもそも入れない**設計にします（オーナー個人情報はガーディアンの検出リストにのみハッシュ等で保持）。

## 7. 成功指標（KPI）

- 配信事故（ガーディアン漏れ）0件
- 配信中のPC負荷超過（設定閾値超え）による中断 0件
- キャラ別: 月間収益、配信時間、平均同接、登録者増加数
- ラウンジ発のナレッジが企画に採用された件数
